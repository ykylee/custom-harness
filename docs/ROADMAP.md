- 상태: **approved** (v2 — 마일스톤별 세부 계획·WBS 로 세분화, 2026-08-25 사용자 승인. 이후 변경은 개정 이력으로 관리)
- 최종 수정일: 2026-08-30
- 관련 문서: [CONCEPT](./CONCEPT.md), [REQUIREMENTS](./REQUIREMENTS.md)

## 진행 모델

**M0 에서 공통 설계를 확정한 뒤, M1 부터 마일스톤마다 미니 SDLC(상세 설계 → 구현 → 테스트 → 릴리스)를 반복**한다. 각 마일스톤의 산출물은 "동작하는 수직 절단" — 매 단계 실제 사용 가능한 물건이 나온다.

```
M0 설계 ─→ M1 코어 수직 절단 ─→ M2 멀티 하네스/멀티 세션 ─→ M3 배포 준비 ─→ M4 확장
(SDLC: 설계)   (구현 시작, MVP)      (1차 기능 완성)             (릴리스 1.0)     (후순위 편입)
```

- 규모 표기: S(반나절~1일) / M(2~4일) / L(1주+), 1인 기준 상대 추정 — 배분·순서 판단용이며 일정 약속이 아니다.
- WBS ID 체계: `<마일스톤>.<작업 패키지>.<태스크>` (예: 1.3.2 = M1 WP1.3 의 2번 태스크). M4 는 트랙형(4.1~4.3 = T1~T3). M5~M7 은 paseo 서비스 분석 기반 도입 웨이브 A~C (2026-08-30 승인).

## 마일스톤 간 핵심 의존

- M0 0.5.1(Windows 실측) → M2 의 Windows 번들 범위 확정 (grok 미지원 시 pi/omp 축소안)
- M0 0.5.2(저장소 유무) → M3 WP3.2 조건부 / M0 0.5.3(서명) → M3 WP3.4 갈래
- M0 0.5.4(게이트웨이 실측: /v1/models·SSE 품질) → M1 수용 기준·M2 2.3.4 방식
- M1 1.3.1(pi RPC base) → M2 2.1(omp 확장) / M1 1.3.4(mock 하네스) → M2 UI 트랙 병렬화의 열쇠
- M3 3.6.4(파일럿 피드백) → M4 트랙 순서 재조정
- **M5 5.0.2(세션 레코드 additive 선반영) → M7 7.1(주의 상태)** — 지금 필드를 넣어두지 않으면 뒤에서 마이그레이션이 생긴다
- **M5(워크스페이스 정본) → M6 전체 / M7 7.1·7.4·7.5** — 탭 타깃과 위임의 소유자가 워크스페이스다
- **M4 T1(스킬/MCP 정본 번들) → M7 7.2.3(역방향 MCP 노출)** — 변환 계층을 재사용한다
- **M6 6.1.2(바이너리 프레임) ← M0 0.2.4 결정의 명시적 재개정** — 개정 사유를 protocol-design 에 남긴다
