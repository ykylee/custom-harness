## 1. 전제와 동봉 대상

전제: 폐쇄망 반입(파일 단위 이관 절차)을 거쳐 배포된다. 외부 레지스트리(npm/brew/GitHub Releases) 접근 불가. 1차 타깃은 pi / oh my pi / grok build (CONCEPT §4).

번들에 들어가는 것:

| pi | npm 패키지 (Node 필요) | MIT |

## 2. 번들 포맷 옵션 비교

| 축 | A. 단일 오프라인 아카이브 + 설치 스크립트 | B. OS 네이티브 패키지 (deb/rpm/msi/pkg) | C. 내부 레지스트리 기반 설치 | D. 컨테이너 이미지 |
|---|---|---|---|---|
| 폐쇄망 반입 | **파일 1개 반입으로 끝** | OS 별 패키지 N개 반입 | 반입 후 레지스트리 게시 절차 추가 | 이미지 반입 + 컨테이너 런타임 전제 |
| OS 다양성 | OS/아키텍처별 아카이브 변형으로 대응 | 포맷 자체가 OS 별로 갈림 (빌드 파이프라인 4종) | 레지스트리가 OS 중립이나 결국 바이너리는 OS 별 | 리눅스 컨테이너로 통일되나 개발자 PC(mac/win)와 괴리 |
| 설치 권한 | **사용자 홈 설치 가능 (관리자 권한 불요)** | 대부분 관리자 권한 필요 | 사용자 홈 가능 | 런타임 설치에 관리자 권한 |
| 버전 세트 고정 | 아카이브 = 버전 세트 (자연스러움) | 패키지 의존성으로 표현 — 관리 복잡 | 개별 패키지 조합 → **세트 보장 어려움** | 이미지 = 버전 세트 (자연스러움) |
| 로컬 파일 작업 | 문제 없음 | 문제 없음 | 문제 없음 | **하네스가 로컬 리포를 다뤄야 해서 마운트/권한 마찰 큼** |
| 조직 IT 관리 | 스크립트 기반 — 표준 관리 도구와 연동 약함 | **IT 배포 도구(SCCM 등)와 최적 연동** | 사내 개발 문화에 따라 다름 | 서버 배포에는 최적, 데스크톱에는 부적합 |

판정:

- **A 가 기본 권장.** 폐쇄망 반입이 파일 1개로 끝나고, 관리자 권한 없이 사용자 홈에 설치되며, 아카이브 자체가 곧 검증된 버전 세트가 된다.
- B 는 조직이 IT 배포 도구로 소프트웨어를 밀어넣는 정책이라면 A 위에 씌우는 2차 포장으로 추가 가능 (A 를 만들면 B 는 파생물).
- C 는 버전 세트 보장이 깨지기 쉬워 단독으로는 비권장. 단, **업데이트 채널의 운반 수단**으로는 유용 (§4).
- D 는 본체를 서버형(데몬)으로 갈 경우 서버 쪽 배포에만 재검토.

## 3. 버전 세트 (manifest)

번들의 핵심 개념은 "검증된 하네스 버전의 불변 세트"다.

- 번들 루트에 `manifest.json`: 번들 버전, 하네스별 (이름, 버전, 체크섬, OS/아키텍처), Node 런타임 버전, 설정 템플릿 버전.
- 본체 어댑터의 COMPAT 정책(버전 검증 + 관대한 파싱 — 인터페이스 조사 §4)이 manifest 의 버전 범위와 연동된다: 어댑터는 "이 번들에서 검증된 버전"임을 기동 시 확인하고, 불일치 시 경고.
- omp 처럼 릴리스가 빠른 하네스도 번들 갱신 주기에만 올라간다 — 개별 하네스의 자체 업데이트는 전부 비활성(§1 스위치 프리셋).

## 4. 업데이트 채널

- **전체 번들 교체(불변 버전 세트)를 권장.** 하네스 개별 패치는 세트 검증을 깨뜨리므로 없음. 업데이트 = 새 번들 반입 → 설치기가 이전 버전 위에 원자적 전환(버전 디렉토리 + 심링크 스위칭), 롤백은 심링크 되돌리기.
- 운반 수단은 사내 환경에 따라 두 갈래:
  - 내부 아티팩트 저장소(Nexus/Artifactory 류)가 있으면: 번들을 거기 게시하고, 본체가 **내부 저장소만** 대상으로 새 버전 확인·다운로드 (외부 참조 0 유지).
  - 없으면: 파일 공유/배포 절차로 수동 반입. 본체는 업데이트 확인 기능 없이 수동 설치만.
- 하네스·본체를 막론하고 외부로 나가는 업데이트 체크는 빌드 시점에 제거/비활성 고정.

### 4.1 구현 규약 (WBS 3.1.1, 2026-09-01)

업데이트는 **별도 경로가 아니라 설치기를 다시 돌리는 것**이다(FR-4.4.1). 그래서 설치기 앞뒤에
판단 셋을 얹었고, 규칙은 두 설치기가 함께 부르는 `tools/versions-tool.mjs` 한 곳에 있다 —
sh 와 PowerShell 에 같은 규칙을 두 번 쓰면 반드시 갈라진다.

| 단계 | 하는 일 |
|---|---|
| `plan` | 신규 설치 / 업그레이드 / 동일 버전 / 다운그레이드 / (형식 비교 불가 시) 버전 교체 판정. **방향을 추측하지 않는다** |
| `guard` | 데몬이 실행 중이면 중단하고 종료 코드 3 (FR-4.4.4). 비대화형이라 동의는 `--force` 로 갈음. 죽은 프로세스의 잔존 pid 는 막지 않는다 |
| `switch` | `current` 를 `rename(2)` 으로 원자 교체 (아래) |
| `prune` | 보존 개수를 넘는 이전 버전 정리. `current` 와 방금 설치한 버전은 **절대** 지우지 않는다. 우선순위 `--keep` > `CUSTOM_HARNESS_KEEP_VERSIONS` > `data/settings.json` 의 `update.keepVersions` > 기본 3 |

`update.keepVersions` 는 설치기만 읽는다. 데몬이 하지 않는 일(디스크 정리)이라 데몬 설정
레지스트리에는 선언하지 않는다.

#### `current` 전환은 셸 `mv` 로 할 수 없다 (2026-09-01 실측)

`current` 가 **디렉토리를 가리키는 심링크**일 때 `mv -f current.new current` 는 목적지 링크를
*따라가서* 새 링크를 그 디렉토리 **안으로** 옮기고 **성공(0)을 반환한다**. 링크는 그대로 남고
실패 폴백도 걸리지 않는다. 결과적으로 **모든 업데이트에서 `current` 전환이 조용히 실패**하고,
옛 버전 디렉토리 안에 `current.new` 잔존물이 남았다. 첫 설치에는 `current` 가 없어 드러나지
않았고, 설치기 검증(2.5.2)이 신규 설치만 다뤄 이 구간이 비어 있었다.

`rename(2)` 은 목적지 심링크를 따라가지 않고 링크 자체를 원자적으로 교체한다. 설치기에는
이미 번들 Node 가 있으므로(FR-4.1.3) 전환을 그쪽으로 옮겼다. Windows 는 junction 이라
`Delete()` → `New-Item -Junction` 이 그대로다(§4 의 비원자 구간은 1차 수용 유지).

검증: `npm run smoke:update` — 도구 로직은 합성 루트로, 설치기 배선은 실제 번들로 격리 루트에
설치해 확인한다. 스모크는 **작업 트리의 설치기·도구를 번들 사본에 덧씌운다**(manifest 는
harnesses·app·configTemplates 만 덮으므로 검증에 영향 없다) — 번들에 구워진 사본을 돌리면
마지막 빌드 시점의 코드를 검증하게 된다.

### 4.2 롤백 (WBS 3.1.2, FR-4.4.2)

롤백은 `current` 를 이전 버전으로 되돌리는 **단일 조작**이다. 세션 데이터는 `data/` 에 있어
버전 디렉토리 밖이므로 손대지 않는다.

**진입점은 `current` 를 거치지 않는다.** 이게 설계의 요점이다 — 롤백은 *current 가 깨졌을 때*
쓰는 것인데, 평소 실행 경로(`bin/custom-harness` → `current/bin/...`)를 타는 도구로는 정작
필요한 순간에 못 쓴다. 그래서 설치기가 `bin/custom-harness-rollback` 을 따로 깔고, 이 스크립트는
`versions/` 를 훑어 **쓸 수 있는 아무 설치본의** 번들 Node 로 도구를 실행한다.

| 명령 | 동작 |
|---|---|
| `custom-harness-rollback --list` | 설치된 버전과 현재 사용 중인 것 |
| `custom-harness-rollback` | **직전 버전**으로 되돌린다 |
| `custom-harness-rollback <버전>` | 지정 버전으로 |

"직전"은 버전 번호가 아니라 **설치 시각**으로 고른다. 다운그레이드한 뒤 롤백하면 "이전"은
번호가 큰 쪽이고, 사용자가 원하는 것은 *방금 떠나온 자리로 돌아가는 것*이기 때문이다.

실행 중 데몬 보호는 설치와 같은 규칙이다(FR-4.4.4) — 종료 코드 3 으로 중단하고 `--force` 가
비대화형 동의를 갈음한다. 되돌아갈 버전이 없거나 이름이 틀리면 설치된 목록을 함께 보여 준다.

검증: `npm run smoke:update` 가 **`current` 를 실제로 깨뜨린 뒤**(최신 버전의 `app/` 삭제)
롤백이 되는지, 그리고 세션 데이터가 남아 있는지까지 확인한다.

### 4.3 실패 주입과 원자성 경계 (WBS 3.1.3, NFR-8)

NFR-8 은 "**어느 단계에서 실패해도** 기존 설치본과 사용자 데이터는 손상되지 않는다"이고
검증 방법까지 못박는다 — "단계별 중단 주입(디스크 부족·권한 오류 모사)".

`npm run smoke:nfr8` 이 실패를 **바깥에서** 주입한다. 설치기에 검증용 훅을 넣지 않는 이유는
그 분기 자체가 검증되지 않은 경로가 되기 때문이다.

| 주입 | 방법 |
|---|---|
| 체크섬 불일치 | 번들 사본의 하네스 파일 훼손 (FR-4.2.1) |
| 권한 오류 | `versions/` 를 `0555` 로 |
| 디스크 부족 | 20MB 램디스크에 설치 (`hdiutil`+`diskutil`, 권한 불요). linux/win 은 C-5 실기기 항목 |
| 단계별 중단 | 설치기가 찍는 `[install] N/7` 표시를 보고 **그 단계에서** SIGKILL (3~7단계) |
| 중단 후 재시도 | 복사 중 SIGKILL → 같은 번들로 다시 설치 |

**시간으로 죽이면 안 된다.** 300ms·1500ms·3000ms 로 죽여 봤자 셋 다 복사 단계에 떨어져
"단계별"이 아니다. 단계 표시를 보고 죽이면 결정적이고 실제로 각 단계를 덮는다.

#### 원자성 경계는 `current` 전환이다

- **전환 전(1~5단계)에서 죽으면**: `current` 는 이전 버전 그대로, 이전 버전 디렉토리 온전,
  `data/` 그대로, 미완성 버전이 정식 이름으로 노출되지 않음(`.partial` 로만 남음).
- **전환 시점 이후(6~7단계)에서 죽으면**: 이미 새 상태로 완결된 것이다. 가리키는 버전이
  무엇이든 **그것이 완전해야** 하고 이전 버전은 롤백 대상으로 보존돼야 한다.

#### 중단이 남긴 `.partial` 이 다음 설치를 오염시켰다 (2026-09-01 실측)

`cp -R src dst` 는 `dst` 가 이미 있으면 그 **안으로** 복사한다. 중단이 남긴
`versions/<name>.partial` 을 지우지 않고 재시도하면 "중단 시점의 불완전한 트리 + 전체 복사본
중첩"이 만들어지는데, **최상위 `manifest.json` 은 남아 있어 정상처럼 보인 채** `current` 가
그것을 가리킨다 — 잘린 바이너리를 품은 설치본이 활성이 될 수 있다. 체크섬 검증은 *설치 대상*이
아니라 *번들 원본*을 보므로 이걸 못 잡는다.

→ 복사 전에 `rm -rf "$TARGET.partial"`(ps1: `Remove-Item -Recurse -Force`). 실패 주입이
잡아야 할 것은 실패 그 자체가 아니라 **실패 뒤의 상태**라는 것을 보여 준 사례다.

## 5. 권장안 (확정)

**OS/아키텍처별 단일 오프라인 아카이브(A) + manifest 기반 불변 버전 세트 + 전체 번들 교체 업데이트.** 사용자 홈 설치(관리자 권한 불요), 설치 시 게이트웨이 설정 템플릿과 오프라인 스위치 프리셋까지 주입해 zero-config 를 완성한다.

## 5. 라이선스 고지 (WBS 3.3.1·3.3.2, FR-4.5·NFR-4)

### 5.1 산출물

빌드가 `licenses/` 를 만든다 — **동봉물의 SSOT 는 번들 자신**이고, 앱도 검수 스크립트도 그것을 읽는다.

| 파일 | 용도 |
|---|---|
| `NOTICE.md` | 사람이 읽는 고지 — 동봉물·버전·라이선스·원문 경로 표 |
| `notices.json` | 같은 표의 기계 판독본 (`{name, version, license, paths[]}`) — 앱 정보 화면이 그린다 |
| `<동봉물>/LICENSE` | 원문 전체. Electron 은 Chromium/Node 서드파티 고지(`LICENSES.chromium.html`, 약 20MB) 포함 |
| `PROVENANCE.md` | 원문의 반입 출처·해시 |

`NOTICE.md` 와 `notices.json` 은 빌드의 **같은 `noticeRows` 에서** 생성한다. 둘을 따로 만들면
어긋나는 날이 오고, 어긋난 쪽이 어느 쪽인지 알 수 없게 된다.

### 5.2 앱에서의 열람

FR-4.5 는 동봉만이 아니라 **앱 정보 화면에서 열람 가능**할 것을 요구한다. 설정 → *앱 정보 ·
오픈소스 고지*(커맨드 팔레트에서도 진입)에서 버전·번들 신원·동봉물 표·원문을 본다.

- 데몬이 `system.about` 으로 색인을, `system.license.read` 로 원문을 준다. 번들 위치는
  `CUSTOM_HARNESS_MANIFEST` 에서 유도한다(`<번들>/licenses/`) — 개발 실행에서는 고지가 없고
  화면은 그 사실을 표시한다.
- 원문은 **조각 단위**로 넘긴다. 20MB Chromium 고지도 열람 대상이므로 한 번에 싣지 않고
  `nextOffset` 으로 이어 읽는다 — 상한을 두고 잘라 버리면 그 원문은 앱에서 열람 불가가 되어
  요건을 못 지킨다. 조각 경계에서 다중바이트 문자가 잘리지 않도록 불완전한 UTF-8 시퀀스는
  다음 조각으로 미룬다. (실측: 19.2MB · 77 조각 · 263ms · 원문 완전 복원)
- 읽기 범위는 `licenses/` 안으로 봉쇄된다(`..`·절대경로·심링크 탈출 거절 — 워크스페이스 파일
  뷰어와 같은 가드). 고지 열람 창구가 번들 임의 파일 읽기로 번지지 않게 하기 위함이다.

### 5.3 검수

`npm run audit:cleanroom` 이 clean-room(NFR-4 ①)과 고지 완전성·정합성(FR-4.5)을 함께 본다.
검사 항목·한계·수행 기록은 [clean-room 검수 기록](../reference/clean-room-audit.md).

### 6-1. grok 바이너리 조달 절차 (2026-08-25 확정 — 사외 실측)

grok 은 GitHub Releases 에 asset 이 없고 x.ai CDN 이 유일 배포 경로이며, **CDN 은 체크섬을 공개하지 않는다**(설치 스크립트도 해시 검증 없이 다운로드). 따라서 사외 빌드 환경에서 아래 절차로 자체 해시를 고정한다.

1. **URL 규칙** (install.sh 실측): `<BASE>/grok-<version>-<os>-<arch>`
   - primary: `https://x.ai/cli/…`, fallback: `https://storage.googleapis.com/grok-build-public-artifacts/cli/…`
   - os·arch 토큰: `macos|linux|windows` × `x86_64|aarch64` (예: `grok-1.0.5-linux-x86_64`)
2. **이중 소스 교차 검증**: primary·fallback 양쪽에서 각각 다운로드 → sha256 일치 확인. 불일치 시 조달 중단(공급망 이상 신호).
3. **바이너리 무결성 확인**: `file` 로 타깃 형식 확인 (linux 는 static-pie ELF — 폐쇄망 glibc 의존 최소화에 유리), 가능하면 실행 스모크(`--version`)는 해당 OS 실기기에서.
4. **고정 기입**: `bundle/sources.json` 의 해당 asset 에 `url`(primary)·`fallbackUrl`·`sha256`·`binaryName` 기입. 빌드 파이프라인(`fetchPinned`)이 이 해시로 다운로드·캐시 검증한다.
5. **버전 갱신 시**: 1~4 를 재수행하고 버전·해시를 함께 교체 (버전 세트 불변성, §3).

2026-08-25 적용 실측: `grok-1.0.5-linux-x86_64` — primary/fallback sha256 동일(`9ba87444…7238`, 159MB) 확인 후 고정, linux 번들 재조립·manifest 검증 통과. 실행 스모크는 linux 실기기(C-5)에서.
