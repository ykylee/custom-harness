# UI 형태 설계 논의

- 문서 목적: CONCEPT §7 미정 항목인 UI 형태(웹/데스크톱/모바일 범위)의 옵션을 비교하고 권장안을 제시한다. 기술 스택 논의의 선행 조건.
- 상태: done (2026-08-24 사용자 확정 — §4. 파생 과제는 기술 스택 논의로 이관)
- 최종 수정일: 2026-08-24
- 관련 문서: [CONCEPT](../CONCEPT.md) §7, [paseo 분석](../reference/paseo-analysis.md) §4·§7, [패키지 배포 형태](./packaging.md)

## 1. 전제

- 폐쇄망, 타깃 3 OS(macOS arm64 / Windows x64 / Linux x64), 사용자 홈 아카이브 설치 ([packaging](./packaging.md) §6).
- paseo 검증 패턴: **데몬 중심 + 얇은 클라이언트** — 하네스 프로세스 관리·상태·영속화는 데몬이 소유하고, UI 는 WebSocket 클라이언트일 뿐 (paseo 분석 §7-1). 이 분리는 UI 형태 선택과 무관하게 유지할 가치가 있으며, **UI 형태 결정 = "데몬에 어떤 클라이언트를 몇 개 붙이느냐"의 결정**이 된다.
- 컨셉 §2 "UI 제공"이 핵심 아이디어이므로 CLI/TUI 단독안은 검토에서 제외 (관리용 최소 CLI 는 별개로 포함).

## 2. 클라이언트 형태 옵션 비교

| 축 | A. 로컬 웹 UI (데몬이 서빙, 브라우저 접속) | B. 데스크톱 앱 (Electron/Tauri 셸) | C. 모바일 앱 |
|---|---|---|---|
| 추가 배포물 | **없음** — 데몬이 정적 웹 번들 서빙, 브라우저는 PC 에 이미 있음 | OS 3종별 앱 빌드 + 코드 서명 | 앱 배포 채널(MDM/스토어) + 릴레이 인프라 |
| 코드 서명/반입 마찰 | **없음** | macOS 공증·Windows 서명은 외부 서비스 필요 — 미서명 시 Gatekeeper/SmartScreen 마찰 | 최대 (사내 MDM 절차) |
| 3 OS 대응 비용 | 웹 빌드 1개 | 빌드 파이프라인 3종 | iOS/Android 별도 |
| 네이티브 통합 (트레이·알림·자동 시작) | 제한적 (브라우저 알림 정도) | **가능** | 푸시 알림 가능 |
| 멀티 에이전트 대시보드 UX | 충분 (탭/페인 패턴은 웹 기술로 동일 구현) | 동일 (같은 웹 코드를 셸에 담음) | 화면 제약 — 모니터링·승인 응답 위주 |
| 폐쇄망 적합성 | **최상** — 외부 의존 0 | 서명 외 외부 의존 없음 | 릴레이 셀프호스팅 필요 |

핵심 관찰: **B 와 C 는 A 의 대체재가 아니라 파생물이다.** paseo 도 데스크톱 패키지에 렌더러 코드가 없고 웹 번들을 셸에 담을 뿐이다(분석 §4.2). 따라서 A 로 시작하면 B/C 는 언제든 추가 가능하고, 그 역은 성립하지 않는다.

## 3. 접속 범위 (A 선택 시 하위 결정)

- **localhost 전용 (기본)**: 데몬이 127.0.0.1 만 바인드. 보안 표면 최소.
- **사내 LAN 접속 허용 (선택)**: 같은 사내망의 다른 기기(노트북 등)에서 자기 데몬에 접속. 토큰 인증 + bind 주소 설정으로 opt-in. paseo 류 E2EE 릴레이는 폐쇄망에서는 과설계 — 사내 LAN 직결이면 충분.

## 4. 결정 사항 (2026-08-24 사용자 확정)

| 항목 | 확정값 | 비고 |
|---|---|---|
| 1차 형태 | **데스크톱 앱 (B)** | 문서 권장은 A(웹 UI)였으나, 네이티브 알림을 1차부터 요구하는 사용자 결정. 단, 2026-09-03 사용자 승인으로 트레이 상주는 제거한다. 구조는 §2 관찰대로 **데몬 + 웹 기술 렌더러를 셸에 담는 형태**를 유지 — 셸에는 렌더러 코드를 두지 않고(paseo §4.2 패턴) 데몬 수명주기 관리만 맡긴다 |
| 모바일 | **범위 제외 확정** | 데몬 분리 구조로 문은 열어둔 채 제외 |
| 접속 범위 | **localhost 전용** | 데몬은 127.0.0.1 만 바인드. LAN opt-in 없음 |
| 브라우저 환경 | 최신 Chromium 계열 표준 | 웹 기술 제약 없음. 데스크톱 셸이라 실사용 의존은 없으나 개발·비상용 브라우저 접속 경로 확보 가능 |

### 파생 과제 (기술 스택 논의로 이관)

- [ ] **셸 선택: Electron vs Tauri** — Electron 은 Chromium+Node 동봉으로 3 OS 렌더링 일관성 확보 + paseo 처럼 `ELECTRON_RUN_AS_NODE` 로 데몬·pi/omp 용 Node 런타임을 겸할 수 있어 **번들의 별도 Node 동봉이 불필요해짐** (packaging §1 과 연동). Tauri 는 경량이나 OS 별 webview 편차 + Linux webkitgtk 의존.
- [ ] **코드 서명 체계 확인** — macOS 공증·Windows 서명은 사외 빌드 시점에 수행 후 반입하는 흐름이 되는데, 조직의 서명 인증서 보유 여부·미서명 배포 허용 여부 확인 필요 (사용자 홈 설치라 Gatekeeper/SmartScreen 마찰이 설치 스크립트로 우회 가능한지 포함).
