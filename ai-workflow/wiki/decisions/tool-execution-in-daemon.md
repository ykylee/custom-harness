# 결정 — 역방향 툴의 실행은 데몬 안에서만 일어난다

**결정일** 2026-09-01 (M7 WBS 7.2.4) · **상태** 유효

역방향 툴 호출은 `tool.invoke` RPC 하나로 데몬에 들어온다. 노출 프로세스(하네스가 spawn 하는 MCP stdio 서버, 그리고 그것을 자식으로 띄우는 pi 확장)는 **목록을 내주고 호출을 전달할 뿐 판단하지 않는다**.

7.2.3 까지는 반대였다 — 노출 프로세스가 `session.list`·`terminal.read` 같은 데몬 RPC 를 직접 불렀다. read 5종만 열려 있는 동안에는 그 구조로 충분했다.

## 왜 옮겼나 — write 를 열려면 셋이 데몬에 있어야 한다

| 필요한 것 | 데몬에만 있는 이유 |
|---|---|
| **승인 채널** | 사용자와 이어진 연결(렌더러 WS)을 데몬이 소유한다. 노출 프로세스에는 물을 상대가 없다 |
| **감사 로그의 단일 기록자** | 하네스마다 MCP 서버 프로세스가 **따로** 뜬다. 각자 JSONL 을 append 하면 줄이 섞인다 — append 원자성은 `PIPE_BUF` 이하에서만 성립하고, 인자를 실은 줄은 쉽게 그보다 길다 |
| **세션 그래프** | 재귀 깊이를 세려면 부모 세션을 알아야 한다 |

셋 다 데몬에 있는데 관문만 밖에 두면, 경로마다 관문을 복제하게 된다. [[decisions/tool-catalog-in-protocol]] 이 *정의*를 한 곳에 모은 것과 같은 이유로 *집행*도 한 곳에 모은다.

## 파생 결정 4가지

### 1. 게이트는 옵션이지만 기본값이 "거부"다

`createToolInvoker` 는 `gate` 콜백을 선택적으로 받고, **없으면 승인 대상 툴을 전부 거부**한다. 테스트 편의가 아니라 기본값의 방향 때문이다 — 게이트를 붙이는 것을 잊은 호출 경로가 생기면 write 가 열리는 것이 아니라 막힌다.

### 2. 호출자는 자기 신고하지 않는다

노출 프로세스가 보내는 것은 **부모 pid** 뿐이고, 데몬이 PID 원장에서 세션을 역인덱싱한다. 세션 ID 를 직접 주장하게 두면 그 값은 하네스가 spawn 한 프로세스의 자기 신고라 검증할 수 없다. 원장은 우리가 spawn 하며 직접 적은 기록이다.

호출자를 판정하지 못하면 **write 는 거부하고 read 는 통과**시킨다. 승인 카드를 붙일 화면이 없다는 뜻이지만, 조회까지 막으면 위임한 세션을 감시하는 일 자체가 불가능해진다.

### 3. 툴 바인딩도 데몬 자신의 RPC 를 다시 탄다

매니저를 직접 부르지 않는다. 워크스페이스 존재 확인·경로 이탈 가드·터미널 소유 확인 같은 방어가 RPC 핸들러 안에 있고, 우회하면 **역방향 툴만 그 방어를 지나지 않는 표면**이 된다.

### 4. 만료는 거부다

승인 대기에는 상한(120초)이 있고, 만료는 실행이 아니라 거부로 끝난다. 무응답을 승인으로 해석하면 사용자가 자리를 비운 사이에 실행된다. 노출 프로세스 쪽 RPC 대기는 그보다 길게(180초) 잡아 "만료로 거부됨"이라는 결과를 모델이 받아볼 수 있게 한다.

## 대가

노출 프로세스가 얇아진 대신 툴 호출마다 WS 왕복이 하나 더 붙는다. 역방향 툴은 초당 수백 번 불리는 경로가 아니고(모델의 턴 단위로 몇 번이다), 그 비용으로 관문 복제를 막는다.
