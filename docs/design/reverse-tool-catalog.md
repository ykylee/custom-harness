# 역방향 툴 카탈로그 (M7 WBS 7.2.2)

- 문서 목적: 데몬이 **자신의 기능을 하네스에게 되돌려 노출**하는 툴의 정본을 확정한다. 이름·파라미터·효과 분류·승인 대상 여부를 여기서 고정하고, 노출 경로(7.2.3)와 안전장치(7.2.4)는 이 표를 전제로 만든다.
- 범위: 카탈로그 정의(§3~5) + 안전장치(§7, 7.2.4) + 위임·비용(§8, 7.3.1·7.3.2). MCP 서버·pi 확장의 **구현**은 7.2.3.
- 대상 독자: 유지보수자, 설계자, AI agent
- 상태: draft (v1.5, 2026-09-01 — §8.5 팬아웃 상한·비용 가시화(7.3.2) 추가, 카탈로그 13종(`session_usage`). v1.4: §8 위임(7.3.1) 추가, 카탈로그 12종으로 확장(`session_wait`·`session_result`). v1.3: §7 안전장치(7.2.4) 확정, `term_new.cwd` 제거. v1.2: §6 에 7.2.3b(pi 확장) 완료 반영. v1.1:  §5 엄격성 정정(`z.object`→`z.strictObject`), §9 결과 스키마 확정, §6 에 7.2.3 실측 반영. v1: 2026-08-31 7.2.2 구현과 함께 작성)

## 1. 왜 프로토콜 층에 두는가

노출 경로가 둘이기 때문이다 (7.2.1 실측으로 확정):

- **omp · grok** — 데몬이 소유한 **MCP stdio 서버 1개**
- **pi** — 같은 카탈로그를 **네이티브 확장**(`pi.registerTool`)으로

두 경로가 각자 툴을 정의하면 하네스마다 다른 표면이 생긴다. 모델이 보는 툴은 하네스와 무관하게 같아야 하고, 그러려면 정의가 양쪽보다 위층에 있어야 한다. 그래서 `@custom-harness/protocol` 이다.

## 2. 이름 규칙 — 짧게

하네스가 **다시 접두사를 붙인다** (실측):

| 하네스 | 모델이 보는 이름 |
|---|---|
| omp | `mcp__<server>_<tool>` → `mcp__ch_session_list` |
| grok | `<server>__<tool>` → `ch__session_list` |

원본이 길면 재접두사 후 다루기 나빠진다. 규칙: 소문자·숫자·`_` 만, **3~24자**(`TOOL_NAME_PATTERN`). 도메인 접두사(`session_`·`ws_`·`term_`)로 묶되 그 이상 길게 쓰지 않는다.

## 3. 카탈로그 (13종)

| 이름 | 효과 | 승인 | 설명 |
|---|---|---|---|
| `session_list` | read | — | 세션 목록·상태. **주의 상태(`requiresAttention`·사유)를 함께 준다** |
| `session_read` | read | — | 한 세션의 타임라인을 `fromSeq` 이후부터 |
| `session_wait` | read | — | 활성 턴 완료 대기 (**상한 있음** — 안 끝나면 `done: false`) |
| `session_result` | read | — | 마지막 턴 결과만 회수 (본문·성패·사용량) |
| `session_usage` | read | — | 자기·자손 토큰 합산, 자식별 내역, 활성 자식 수 |
| `session_new` | write | ✅ | 새 세션 생성 (**재귀 위험** — 7.2.4 상한 대상) |
| `session_say` | write | ✅ | 프롬프트 전송 (턴 시작, 완료를 기다리지 않음) |
| `session_stop` | write | ✅ | 진행 중인 턴 중단 (멱등) |
| `ws_list` | read | — | 워크스페이스 목록 |
| `term_list` | read | — | 터미널 목록 |
| `term_new` | write | ✅ | 터미널 열기 (cwd 는 워크스페이스가 정한다 — 7.2.4 에서 파라미터 제거) |
| `term_send` | write | ✅ | 터미널 입력 — **카탈로그에서 가장 위험하다**(임의 셸) |
| `term_read` | read | — | 터미널 스크롤백 읽기 |

FR-9.2 가 열거한 범위(세션 생성·프롬프트 전송·상태 조회·중단·워크스페이스 조회·터미널 조작)를 모두 덮는다 — 테스트가 이 대응을 고정한다. `session_wait`·`session_result` 는 7.3.1 이 더한 위임용 2종이고(FR-9.3 "완료를 기다리거나 결과를 회수"), `session_usage` 는 7.3.2 가 더한 비용 조회다.

### 주의 상태는 다시 계산하지 않는다

`session_list` 가 싣는 주의 상태는 **7.1 의 데몬 정책 모듈이 계산한 값 그대로**다. 툴 층에서 "무엇이 급한가"를 다시 판단하면 UI 와 에이전트가 서로 다른 답을 보게 된다 — 7.1 이 없애려던 문제를 툴 표면에서 되살리는 꼴이다.

## 4. 승인은 우리가 소유한다

`approval` 은 하네스 자신의 승인 게이트와 **별개**다. 하네스는 우리 MCP 서버를 **한 덩어리**로 볼 뿐이라 "세션 목록 조회"와 "임의 셸 입력"을 구분하지 못한다 — grok 은 서버 단위로 `always-allow` 를 제안하기까지 한다(7.2.0b 실측). 그 구분을 카탈로그가 소유한다.

규칙 두 줄, 테스트로 고정:

- **`effect: 'write'` 인 툴은 전부 승인 대상**이다.
- **`effect: 'read'` 인 툴은 승인을 요구하지 않는다** — 조회까지 막으면 위임한 세션을 감시하는 것 자체가 불가능해진다.

## 5. 파라미터 스키마

`z.strictObject` 를 쓴다. 프로토콜의 다른 와이어 스키마가 `looseObject` 인 것과 다른데, 그 관례는 "번들 버전이 다른 양쪽이 서로의 추가 필드를 견딘다"를 위한 것이고 **카탈로그와 그 핸들러는 같이 배포된다**. 반면 여기 입력을 만드는 쪽은 모델이라 오타·환각 파라미터가 조용히 무시되면 안 된다 — 명시적인 검증 실패가 낫다.

> **정정 (2026-09-01, 7.2.3)**: v1 은 `z.object` 를 "엄격"이라고 적었으나 **틀렸다.** zod 의 `z.object` 는 미지 키를 *조용히 제거*할 뿐 거부하지 않는다(`{b:1}` → `{}`, `success: true`). 7.2.3 e2e 가 `ws_list({projectID})` 를 통과시키며 이를 드러냈고, 카탈로그 전체를 `z.strictObject` 로 교정했다. JSON Schema 에도 `additionalProperties: false` 로 실린다. 카탈로그 테스트가 두 성질을 고정한다.

`toolDescriptor()` 가 zod → JSON Schema(2020-12)로 변환한다. MCP `tools/list` 와 pi 확장이 같은 산출물을 쓴다.

## 6. 노출 경로 구현 이력 (7.2.3)

- **7.2.3a — 완료 (2026-09-01)**: MCP stdio 서버(omp·grok) + 등록 절차 + 핸들러의 데몬 RPC 바인딩. read 5종 동작, write 5종은 승인 채널 부재로 명시 거부.
  - **준비 완료 게이트는 재정의됐다.** omp 는 MCP 서버를 **첫 턴이 시작될 때** 띄운다(세션 생성 후 8초를 기다려도 서버 프로세스조차 없다 — 7.2.3 실측). 그래서 "첫 턴 전에 기다리는" 게이트는 성립하지 않고, 1턴째 미노출은 구조적이다. 게이트는 **2턴째 이후의 경합**만 막는다(`get_state.dumpTools` 에 `mcp__*` 가 보일 때까지 한도 내 대기, 초과해도 턴은 나간다).
- **7.2.3b — 완료 (2026-09-01)**: pi 확장(`pi.registerTool`). 확장은 **카탈로그를 알지 못한다** — 데몬의 MCP 서버를 자식으로 띄우고 `tools/list` 로 받은 것을 그대로 pi 에 옮긴다. 여기에 카탈로그를 다시 적으면 정의가 둘이 되고 승인 게이트·파라미터 검증·결과 추림이 갈라진다.
  - 설치는 `$PI_CODING_AGENT_DIR/extensions/ch-reverse-tools.ts`(pi 환경변수 문서: 이 변수가 `~/.pi/agent` 를 대체한다). `--extension` 플래그 대신 이 경로를 쓰면 재개(`--session`) 경로에서도 자동으로 붙는다.
  - **`parameters` 는 생 JSON Schema 로 받는다** — pi 문서는 TypeBox(`Type.Object`)를 쓰지만 그것도 런타임에는 JSON Schema 이고, `toolDescriptor()` 산출물이 그대로 통했다(실측). 변환층 불필요.
  - spawn 사양은 **env 로 넘긴다**(`CUSTOM_HARNESS_MCP_COMMAND`/`_ARGS`) — 파일에 구우면 번들 갱신 시점이 어긋날 때 없는 실행 파일을 가리킨 채로 남는다.
  - pi 는 이름에 접두사를 붙이지 않는다 — 모델이 보는 이름이 `session_list`·`ws_list` 그대로다(omp `mcp__ch_*`, grok `ch__*` 와 다른 지점).
- **7.2.4 — 완료 (2026-09-01)**: opt-in(기본 off) · 승인 채널 · 재귀 깊이 상한 · 감사 로그 · 서버명 선점 탐지. 자세한 결정은 §7.

## 7. 안전장치 (7.2.4)

**실행이 데몬 안으로 들어왔다.** 7.2.3 까지 노출 프로세스(MCP 서버·pi 확장)가 데몬 RPC 를 직접 불렀지만, 7.2.4 는 `tool.invoke` RPC 하나로 좁혔다. 이유 셋:

1. **승인 채널이 데몬에만 있다** — 사용자와 이어진 연결을 데몬이 소유한다.
2. **감사 로그의 기록자는 하나여야 한다** — 하네스마다 MCP 서버 프로세스가 따로 뜨므로 각자 JSONL 을 append 하면 줄이 섞인다(append 원자성은 `PIPE_BUF` 이하에서만 성립하고, 인자를 실은 줄은 쉽게 그보다 길다).
3. **재귀 상한이 보는 세션 그래프가 데몬에 있다.**

노출 프로세스는 목록을 카탈로그에서 그대로 내주고 실행은 넘긴다 — 판단하지 않는다.

### 7.1 opt-in (`tools.reverseExposure`, 기본 off)

홈 격리(`harness.homeIsolation`, 기본 on)와 **기본값 방향이 반대**다. 그쪽은 끄는 것이 위험이고 이쪽은 켜는 것이 위험이다 — 켜면 하네스가 다른 세션을 읽고, 프롬프트를 보내고, 터미널에 입력한다.

끄면 등록을 **지운다**(`unregisterOmpMcpServer` / `grok mcp remove` / 확장 파일 삭제). 항목을 남겨 두면 하네스가 서버를 계속 spawn 하고, 모델에게는 부를 때마다 거부되는 툴 10개가 보인다 — 사용자에게는 설정이 안 먹은 것처럼 보인다.

opt-in 값은 **호출 시점에** 다시 읽는다. 기동 시 굳히면 설정을 끈 뒤에도 이미 떠 있는 MCP 서버가 계속 통과한다.

### 7.2 승인 채널 — 하네스 승인과 같은 길로

역방향 툴 승인은 **데몬이 스스로 만든** `permission_requested` 이벤트로 나간다. 별도 채널을 만들지 않은 이유는 UI 다: 사이드바 배지·주의 상태(7.1)·승인 카드·OS 알림이 이미 이 채널을 소비하므로, 새 채널은 그 전부를 두 번 구현하게 만든다. 구분은 요청의 `origin: 'reverse_tool'` 이 한다(생략 = `harness`, additive).

응답 경로만 다르다 — 하네스 요청은 어댑터로 되돌아가지만 이것은 데몬 안에서 끝난다. 그래서 세션 매니저가 대기 맵을 둘로 나눠 들고(`pending` 은 조회·UI 용 합본, `daemonPending` 은 응답 경로용) 응답 때 출처를 되짚지 않는다.

**만료는 거부다**(기본 120초). 무응답을 승인으로 해석하면 자리를 비운 사이에 실행된다. 노출 프로세스 쪽 RPC 타임아웃은 그보다 길게(180초) 잡아 "만료로 거부됨"이라는 결과를 모델이 받아볼 수 있게 한다.

**물을 곳이 없으면 거부한다.** 호출자 세션을 판정하지 못하면 승인 카드를 붙일 화면이 없다 — 그때 write 툴은 실행하지 않는다. 반면 **조회는 통과시킨다**: 감시가 먼저 죽으면 안 된다.

### 7.3 호출자 판정 — 자기 신고를 믿지 않는다

노출 프로세스는 **부모 pid** 만 보낸다(`callerPid`). 데몬이 PID 원장(`processes.json`)에서 세션을 역인덱싱한다. 세션 ID 를 직접 주장하게 두지 않는 이유: 그 값은 하네스가 spawn 한 프로세스의 자기 신고라 검증할 수 없다. 원장은 우리가 spawn 하며 직접 적은 기록이다.

### 7.4 재귀 상한 (`tools.maxSessionDepth`, 기본 1)

`spawnsSession` 이 붙은 툴(`session_new`)에만 건다. 깊이는 **세션 레코드의 라벨**에 적는다(`ch.parentSessionId`·`ch.toolDepth`) — 데몬 메모리에 두면 재시작으로 깊이가 0 으로 돌아가 상한이 재시작 횟수만큼 우회된다.

상한 판정은 **승인보다 앞선다**. 어차피 못 할 일로 사용자를 깨우지 않는다.

부모-자식 관계의 온전한 모델은 7.3.1 이 이 라벨 위에 세운다.

### 7.5 감사 로그 (`logs/reverse-tools.jsonl`)

통과·거부·실패를 **모두** 남긴다. 거부가 기록되지 않으면 "하네스가 무엇을 하려 했는가"가 사라지는데, 사후 조사에서는 성공보다 그쪽이 중요할 때가 많다. 인자는 요약해 싣는다(긴 문자열은 앞부분 + 길이) — 통째로 남기면 감사 로그가 사실상 프롬프트·터미널 입력의 사본이 된다. 기록 실패는 삼킨다: 디스크 문제 하나가 역방향 툴 전체를 멈추면 안 된다.

### 7.6 서버명 선점 탐지

omp·grok 둘 다 프로젝트 스코프 `.mcp.json` 이 사용자 스코프를 덮는다(7.2.1 §3.5). 워크스페이스가 임의 저장소를 여는 구조라, 저장소가 `ch` 를 미리 차지해 두면 모델이 부르는 `ch__session_list` 가 그 저장소의 서버로 간다.

**막지 않고 알린다.** 그 파일을 읽는 것은 하네스이고 우리는 그 결정에 개입하지 않는다. 저장소가 자기 MCP 서버를 두는 것 자체는 정상이므로 세션 생성도 막지 않는다 — 조용히 바꿔치기되는 것과 알고 쓰는 것의 차이가 조치다.

### 7.7 자동 승인과의 관계 (열린 항목)

`autoApprove` 설정이 켜져 있으면 렌더러가 승인 카드에 자동 응답하므로 역방향 툴 승인도 자동 통과한다. 사용자가 "전부 자동 승인"을 선택한 결과라 의도와 어긋나지 않지만, **역방향 툴만 따로 두는 정책**(예: `term_send` 는 자동 승인에서 제외)이 필요한지는 FR-1.5 후속에서 판단한다.

## 8. 위임 (7.3.1)

FR-9.3 은 "다른 세션을 자식으로 생성하고, 완료를 기다리거나 결과를 회수한다"를 요구한다. 생성은 7.2.4 가 `session_new` + 부모·깊이 라벨로 이미 했고, 여기서는 나머지 셋을 채운다.

### 8.1 관계는 라벨뿐 — 별도 인덱스를 두지 않는다

자식 목록은 `session_list({parentSessionId})` 로 얻고, 그 필터는 **툴 층에서 라벨을 거른다**(`requiresAttention` 과 같은 방식). 데몬에 부모→자식 인덱스를 따로 두면 그것과 라벨이 어긋날 자리가 생긴다 — 관계의 정본은 세션 레코드 하나여야 한다.

그래서 `session_list` 결과 요약에 `labels` 를 싣는다. 빼면 모델이 자기가 만든 자식을 되찾을 수 없다.

### 8.2 대기는 상한이 있다

`session_wait` 는 최대 `timeoutMs`(기본 60초, 상한 120초)만 기다리고, 안 끝났으면 `done: false` 로 돌아온다. 무한 대기를 두지 않는 이유는 전송이다 — 이 호출은 하네스가 spawn 한 MCP 서버의 RPC 를 타고 오고 그쪽 대기도 유한하다. 끊긴 대기보다 다시 거는 편이 낫다.

결과에 **"다시 호출하면 이어서 기다린다"를 명시**한다. 모델이 `timedOut` 을 실패로 읽고 포기하면 위임이 거기서 끊긴다.

데몬 쪽은 `activeTurnId` 가 사라지는 **모든** 경로에서 대기를 푼다 — 정상 종료·실패·중단·비정상 종료(status=error)·세션 닫힘. 하나라도 빠뜨리면 그 경로에서 대기가 상한까지 매달린다.

### 8.3 회수는 마지막 턴만

`session_result` 는 마지막 `turn_started` 이후의 assistant 본문만 잇는다. `session_read` 로도 읽히지만 그쪽은 타임라인 전체라, 부모가 자식의 툴 실행 기록까지 컨텍스트에 싣게 된다 — 위임으로 아끼려던 것을 되돌려 놓는 꼴이다.

턴 경계를 `turnId` 가 아니라 **위치**로 잡는다: `message_delta` 의 `turnId` 는 선택 필드라 어댑터에 따라 비어 있다.

진행 중이면 `pending: true` 와 지금까지 온 본문을 준다 — 중간 상태를 감추면 부모가 "왜 비었나"를 판단할 수 없다.

### 8.4 대기·회수는 승인 대상이 아니다

둘 다 `effect: 'read'` 다. 상태를 바꾸지 않고, 조회를 막으면 위임한 작업을 감시하는 일 자체가 불가능해진다(§4 규칙 그대로).

### 8.5 팬아웃 상한과 비용 가시화 (7.3.2)

FR-9.3 은 위임에 **"팬아웃 개수 상한과 사용량 합산 표시를 필수로"** 요구한다(NFR-7 토큰 절약).

**상한은 둘이 나뉜다.** `tools.maxSessionDepth` 가 트리의 *높이*를 막고, `tools.maxFanout`(기본 1)이 *너비*를 막는다 — 깊이 1 에서도 자식 20개를 동시에 돌리면 토큰은 그대로 20배다. 기본 1 은 "위임은 되지만 병렬은 사용자가 명시적으로 연다"는 뜻이다.

세는 대상은 **닫히지 않은** 자식이다. 닫힌 세션은 더 이상 프롬프트를 받지 못하므로 예산을 쓰지 않는다 — 그것까지 세면 상한이 "누적 생성 수"가 되어 자식 재사용을 막는다.

**게이트와 모델이 같은 함수로 센다.** `session_usage` 가 모델에게 보여 주는 `activeChildCount` 와 게이트가 검사하는 값이 같은 `usageTree()` 에서 나온다. 기준이 갈라지면 모델은 여유가 있다고 보는데 게이트는 막는 상태가 된다.

**거부는 다음 수단을 알려 준다.** 팬아웃 거부문에 `session_usage`(무엇이 비싼지 보기)와 `session_say`(기존 자식에게 이어서 시키기)를 적는다. 막고 끝내면 모델이 갈 곳을 잃고 위임이 멎는다.

**합산은 own 과 subtree 를 나눠 준다.** 부모의 대화가 싸도 위임이 비쌀 수 있고, 그 구분이 없으면 "왜 예산이 줄었나"를 판단할 수 없다. 보고되지 않은 항목은 0 으로 채우지 않는다 — "안 씀"과 "모름"이 섞이면 합계가 거짓이 된다. 트리를 걸을 때 방문 집합을 드는 이유는 성능이 아니라 **정지 보장**이다: meta 를 손으로 고쳐 순환이 생기면 조회 한 번으로 데몬이 멎는다.
