# 역방향 툴 카탈로그 (M7 WBS 7.2.2)

- 문서 목적: 데몬이 **자신의 기능을 하네스에게 되돌려 노출**하는 툴의 정본을 확정한다. 이름·파라미터·효과 분류·승인 대상 여부를 여기서 고정하고, 노출 경로(7.2.3)와 안전장치(7.2.4)는 이 표를 전제로 만든다.
- 범위: 카탈로그 정의. MCP 서버·pi 확장의 **구현**은 7.2.3, opt-in·상한·감사 로그는 7.2.4.
- 대상 독자: 유지보수자, 설계자, AI agent
- 상태: draft (v1.1, 2026-09-01 — §5 엄격성 정정(`z.object`→`z.strictObject`), §7 결과 스키마 확정, §6 에 7.2.3 실측 반영. v1: 2026-08-31 7.2.2 구현과 함께 작성)
- 최종 수정일: 2026-09-01
- 입력: [FR-9.2](../requirements/fr9-orchestration.md), [하네스 MCP 지원 실측](../reference/harness-mcp-support.md)
- 구현: `packages/protocol/src/tools.ts`

## 1. 왜 프로토콜 층에 두는가

노출 경로가 둘이기 때문이다 (7.2.1 실측으로 확정):

- **omp · grok** — 데몬이 소유한 **MCP stdio 서버 1개**
- **pi** — 같은 카탈로그를 **네이티브 확장**(`pi.registerTool`)으로

두 경로가 각자 툴을 정의하면 하네스마다 다른 표면이 생긴다. 모델이 보는 툴은 하네스와 무관하게 같아야 하고, 그러려면 정의가 양쪽보다 위층에 있어야 한다. 그래서 `@custom-harness/protocol` 이다.

## 2. 이름 규칙 — 짧게

하네스가 **다시 접두사를 붙인다** (실측):

| 하네스 | 모델이 보는 이름 |
|---|---|
| omp | `mcp__<server>_<tool>` → `mcp__ch_session_list` |
| grok | `<server>__<tool>` → `ch__session_list` |

원본이 길면 재접두사 후 다루기 나빠진다. 규칙: 소문자·숫자·`_` 만, **3~24자**(`TOOL_NAME_PATTERN`). 도메인 접두사(`session_`·`ws_`·`term_`)로 묶되 그 이상 길게 쓰지 않는다.

## 3. 카탈로그

| 이름 | 효과 | 승인 | 설명 |
|---|---|---|---|
| `session_list` | read | — | 세션 목록·상태. **주의 상태(`requiresAttention`·사유)를 함께 준다** |
| `session_read` | read | — | 한 세션의 타임라인을 `fromSeq` 이후부터 |
| `session_new` | write | ✅ | 새 세션 생성 (**재귀 위험** — 7.2.4 상한 대상) |
| `session_say` | write | ✅ | 프롬프트 전송 (턴 시작, 완료를 기다리지 않음) |
| `session_stop` | write | ✅ | 진행 중인 턴 중단 (멱등) |
| `ws_list` | read | — | 워크스페이스 목록 |
| `term_list` | read | — | 터미널 목록 |
| `term_new` | write | ✅ | 터미널 열기 |
| `term_send` | write | ✅ | 터미널 입력 — **카탈로그에서 가장 위험하다**(임의 셸) |
| `term_read` | read | — | 터미널 스크롤백 읽기 |

FR-9.2 가 열거한 범위(세션 생성·프롬프트 전송·상태 조회·중단·워크스페이스 조회·터미널 조작)를 모두 덮는다 — 테스트가 이 대응을 고정한다.

### 주의 상태는 다시 계산하지 않는다

`session_list` 가 싣는 주의 상태는 **7.1 의 데몬 정책 모듈이 계산한 값 그대로**다. 툴 층에서 "무엇이 급한가"를 다시 판단하면 UI 와 에이전트가 서로 다른 답을 보게 된다 — 7.1 이 없애려던 문제를 툴 표면에서 되살리는 꼴이다.

## 4. 승인은 우리가 소유한다

`approval` 은 하네스 자신의 승인 게이트와 **별개**다. 하네스는 우리 MCP 서버를 **한 덩어리**로 볼 뿐이라 "세션 목록 조회"와 "임의 셸 입력"을 구분하지 못한다 — grok 은 서버 단위로 `always-allow` 를 제안하기까지 한다(7.2.0b 실측). 그 구분을 카탈로그가 소유한다.

규칙 두 줄, 테스트로 고정:

- **`effect: 'write'` 인 툴은 전부 승인 대상**이다.
- **`effect: 'read'` 인 툴은 승인을 요구하지 않는다** — 조회까지 막으면 위임한 세션을 감시하는 것 자체가 불가능해진다.

## 5. 파라미터 스키마

`z.strictObject` 를 쓴다. 프로토콜의 다른 와이어 스키마가 `looseObject` 인 것과 다른데, 그 관례는 "번들 버전이 다른 양쪽이 서로의 추가 필드를 견딘다"를 위한 것이고 **카탈로그와 그 핸들러는 같이 배포된다**. 반면 여기 입력을 만드는 쪽은 모델이라 오타·환각 파라미터가 조용히 무시되면 안 된다 — 명시적인 검증 실패가 낫다.

> **정정 (2026-09-01, 7.2.3)**: v1 은 `z.object` 를 "엄격"이라고 적었으나 **틀렸다.** zod 의 `z.object` 는 미지 키를 *조용히 제거*할 뿐 거부하지 않는다(`{b:1}` → `{}`, `success: true`). 7.2.3 e2e 가 `ws_list({projectID})` 를 통과시키며 이를 드러냈고, 카탈로그 전체를 `z.strictObject` 로 교정했다. JSON Schema 에도 `additionalProperties: false` 로 실린다. 카탈로그 테스트가 두 성질을 고정한다.

`toolDescriptor()` 가 zod → JSON Schema(2020-12)로 변환한다. MCP `tools/list` 와 pi 확장이 같은 산출물을 쓴다.

## 6. 7.2.3 · 7.2.4 로 넘기는 것

- **7.2.3a — 완료 (2026-09-01)**: MCP stdio 서버(omp·grok) + 등록 절차 + 핸들러의 데몬 RPC 바인딩. read 5종 동작, write 5종은 승인 채널 부재로 명시 거부.
  - **준비 완료 게이트는 재정의됐다.** omp 는 MCP 서버를 **첫 턴이 시작될 때** 띄운다(세션 생성 후 8초를 기다려도 서버 프로세스조차 없다 — 7.2.3 실측). 그래서 "첫 턴 전에 기다리는" 게이트는 성립하지 않고, 1턴째 미노출은 구조적이다. 게이트는 **2턴째 이후의 경합**만 막는다(`get_state.dumpTools` 에 `mcp__*` 가 보일 때까지 한도 내 대기, 초과해도 턴은 나간다).
- **7.2.3b**: pi 확장(`pi.registerTool`) — 같은 카탈로그를 두 번째 표면으로.
- **7.2.4**: 세션 생성 시 opt-in(기본 off), `spawnsSession` 기반 깊이·개수 상한, 감사 로그, **서버명 선점 탐지**(프로젝트 `.mcp.json` 이 사용자 스코프를 덮는다 — 7.2.1 §3.5).

## 7. 미해결

- ~~툴 **결과** 스키마~~ → **확정 (2026-09-01, 7.2.3)**: MCP `tools/call` 결과는 **텍스트 콘텐츠 1개**(`content: [{type:'text', text}]`)이고 본문은 JSON 문자열이다. 실패도 프로토콜 오류가 아니라 `isError: true` 인 결과로 돌려준다 — 프로토콜 오류로 올리면 하네스가 대화 밖에서 삼켜 **모델이 보지 못한다**. 데몬 응답을 그대로 흘리지 않고 툴마다 추린다: `session_list` 는 승인 원문 대신 개수만, `term_read` 는 base64 대신 디코드한 텍스트를 준다.
- `term_send` 를 승인 대상으로 두더라도 **무엇을 승인하는지** 사용자에게 보여주는 방식(입력 원문 전체 vs 요약)은 7.2.4 UI 항목이다.
