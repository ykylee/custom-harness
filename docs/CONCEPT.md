## 1. 한 줄 요약

폐쇄망 사내망에서, 오픈소스 코딩 에이전트 하네스들을 동봉 설치하고 게이트웨이 연결까지 사전 구성해, 하나의 데스크톱 UI 로 선택·사용하게 하는 오케스트레이션 도구. (paseo 류의 폐쇄망·조직 배포 변형)

## 2. 핵심 아이디어

- **UI 제공**: 사용자는 하네스별 CLI 를 직접 다루는 대신 통합 UI(데스크톱 앱)를 통해 에이전트를 사용한다.
- **하네스 래핑**: pi, oh my pi, grok build 등 여러 코딩 에이전트 하네스를 각각 래핑한다 (에이전트 루프는 하네스가 소유).
- **선택 사용**: 래핑된 하네스 중 원하는 것을 골라 사용할 수 있다.
- **동봉 배포**: 하네스는 사용자가 따로 설치하는 것이 아니라 이 도구의 설치 패키지에 함께 들어 있다.

## 3. 레퍼런스

- **paseo** ([getpaseo/paseo](https://github.com/getpaseo/paseo), 14.9k★) — "One interface for Claude Code, Codex, Copilot, OpenCode, and Pi agents"
  - 로컬 체크아웃: `~/repos/paseo` (shallow clone)
  - **상세 분석 완료**: [paseo 구성 상세 분석](./reference/paseo-analysis.md) — 데몬 중심 아키텍처, 하네스 추상화(`AgentClient`/`AgentSession`), 프로토콜/릴레이, 멀티 에이전트 UI 패턴, 플러그인 시스템, 인프라 전반.
  - ⚠ **AGPL-3.0-or-later — 코드 재사용 금지.** 패턴·인터페이스 설계만 분석 문서를 매개로 참고한다 ([기술 스택 논의 §5](./design/tech-stack.md)).

## 4. 지원 하네스

편성 원칙: **오픈소스 우선** (2026-08-24 결정). 하네스 동봉 패키지 배포(§6-1)가 전제이므로 재배포 가능한 라이선스가 1차 조건이며, 재배포 조건이 폐쇄적인 하네스(Claude Code, Codex)는 후순위로 미룬다.

### 1차 타깃 (오픈소스 + 게이트웨이 직결)

1. **pi** — MIT. Chat Completions 직결, `PI_OFFLINE` 완비 — 폐쇄망 적합성 최상
2. **oh my pi** — MIT. pi 포크로 pi 어댑터의 공용 base 를 그대로 확장
3. **grok build** — Apache 2.0. air-gapped 배포가 공식 설계에 반영됨, 직결 가능

### 이후 확장

4. **opencode** — 오픈소스지만 런타임 npm 설치·models.dev 페치 의존 → 사전 캐시/내부 미러 구축 후 편입 (조건부)
5. **claude (Claude Code)** — 비오픈소스(재배포 조건 폐쇄적) + Messages 전용이라 변환 프록시 필요 → 후순위
6. **codex** — 재배포 조건 폐쇄적 + Responses 전용이라 변환 프록시 필요 → 후순위

### 제외

- **antigravity** — 폐쇄망에서 게이트웨이 연결이 사실상 불가하여 지원 목록에서 제외 (2026-08-24 결정). 근거: [게이트웨이 호환 조사](./reference/gateway-compatibility.md).

- 통합 인터페이스 조사 완료 — [하네스 인터페이스 조사](./reference/harness-interfaces.md). pi/omp 는 JSONL RPC, grok build 는 headless stream-json 또는 ACP 로 래핑 가능.
- **게이트웨이 호환 조사 완료** — [게이트웨이 호환 조사](./reference/gateway-compatibility.md). 1차 타깃 3종은 전부 Chat Completions 직결 — **1차 범위에서는 변환 프록시가 필요 없다.** 변환 계층(LiteLLM 류)은 claude/codex 편입 시점의 과제로 이동.
- **확장 공유 조사 완료** — [스킬/MCP/플러그인 공유 조사](./reference/extension-sharing.md). 스킬은 SKILL.md 표준으로 무변환 공유 가능, MCP 는 서버 1개 + 설정 변환, 플러그인은 내용물만 공유 가능.

## 5. 운영 환경 제약 (사내망)

이 도구는 **사내망에서 사용**된다. 이 제약이 컨셉의 성격을 규정한다.

- **외부 네트워크 참조 최소화**: 폐쇄망 전제. 외부 API·CDN·원격 서비스 의존을 최소화해야 한다.
- **모델 연결은 지정 게이트웨이로만**: 하네스가 모델 프로바이더를 직접 호출하지 않고, 모든 LLM 트래픽이 **커스텀 게이트웨이**를 경유해야 한다.
- **게이트웨이는 현재 OpenAI 호환 API만 제공**: 하네스가 다른 API 형식을 쓰면 **변환(컨버전)이 필요**하다.
  - 이 제약이 §4 오픈소스 우선 편성과 맞물려 1차 타깃을 "Chat Completions 직결 가능한 하네스"로 좁혔다 — **1차 범위의 기본 요건은 "하네스 엔드포인트를 게이트웨이로 돌리는 설정 주입"이고, API 형식 변환 계층은 claude/codex(Messages/Responses 전용) 편입 시점의 확장 요건**이다.
- **토큰 제약 있음**: 토큰 예산이 제한적이므로, 같은 작업을 여러 하네스에 중복 실행하는 크로스 하네스 오케스트레이션은 가치가 낮을 수 있다.

## 6. 차별점 (vs paseo)

사내망 제약이 곧 차별점의 원천이다. paseo 는 개방망·개인 개발자 전제이고, 이 도구는 폐쇄망·조직 배포 전제다.

1. **하네스 동봉 패키지 배포** — 설치 패키지에 지원 하네스가 함께 들어 있어, 도구를 설치하면 지원 하네스도 같이 설치된다.
   - paseo 는 각 하네스를 사용자가 npm/brew 등에서 직접 설치·로그인해 두었다는 전제 위에서 동작한다. 폐쇄망에서는 외부 레지스트리 접근이 막혀 이 전제 자체가 성립하지 않는다.
   - 동봉 배포는 단순 편의가 아니라 폐쇄망에서의 **성립 조건**이며, 부수 효과로 "버전 호환이 검증된 하네스 세트"를 조직 단위로 통제·배포할 수 있다.
   - 1차 타깃 3종(pi/omp/grok build)은 전부 MIT·Apache 2.0 이라 **동봉 재배포에 라이선스 장애가 없다.** 재배포 조건이 폐쇄적인 claude/codex 는 후순위(§4).
2. **게이트웨이 호환 계층 내장** — 모든 하네스의 LLM 트래픽을 커스텀 게이트웨이(OpenAI 호환)로 라우팅한다. 1차 타깃은 전부 직결이므로 설정 주입만으로 충분하고, Anthropic Messages / OpenAI Responses 형식 변환은 claude/codex 편입 시점의 확장 과제다. paseo 는 각 하네스의 기본 프로바이더 연결을 그대로 쓴다.
3. **설치 즉시 사용 가능한 사전 구성(zero-config)** — 1+2 의 결합 효과. 동봉된 하네스가 게이트웨이 연결 설정까지 주입된 상태로 설치되므로, 사용자는 하네스별 설치·인증·엔드포인트 설정 없이 UI 에서 바로 사용한다.
   - 성립 조건 하나가 미해결: **사용자별 게이트웨이 크리덴셜(API 키) 프로비저닝** — 키 발급·주입 흐름을 설치 과정에 어떻게 통합할지는 설계 단계 과제 (§7).
4. **(후순위) 확장 공유** — 스킬(SKILL.md)은 무변환 공유 가능([확장 공유 조사](./reference/extension-sharing.md)). 조직 공용 스킬/MCP 세트를 패키지에 동봉하는 축으로 확장 가능.

- 크로스 하네스 오케스트레이션(같은 작업 다중 실행)은 토큰 제약으로 차별점 축에서 제외.
